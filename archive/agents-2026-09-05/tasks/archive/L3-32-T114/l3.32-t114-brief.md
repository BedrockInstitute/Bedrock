## THE OWNER'S REQUEST

> Build a Dashboard for me: a visual board webpage, showing by category:
> the current route's flowchart; the remaining lines in the ledger (current
> plus estimate); the current cold-start seconds (current only, no estimate);
> the project code hierarchy and where we are in it; and the orchestrator's own
> workbench state: what is dispatched now, what is queued next, and what
> condition triggers what.
>
> And: **every time a sub-agent returns, the dashboard must be updated.** Not
> every part every time, but every return checks what can and should be
> updated, and updates it.

## THE DESIGN DECISION THAT MAKES THE THIRD REQUIREMENT CHEAP

**The dashboard must be GENERATED from the canonical data, never hand-written.**

If it is hand-maintained, "update it on every return" is manual toil that will
decay exactly like every other manual discipline this project has measured
failing. If it is generated, updating is one command, and staleness becomes
checkable.

So the deliverable is `scripts/dashboard.py`, emitting a self-contained HTML
page to `_build/dashboard.html`, plus a `make dashboard` target.

## THE DATA SOURCES, ALL MACHINE-READABLE

| panel | source | how |
|---|---|---|
| remaining lines, current plus estimate | `dev/ledger.toml` | `[[remaining]]` rows carry the estimates; `python3 scripts/ledger.py --brief` prints standing measured from HEAD. Both calibers exist: naive and calibrated |
| cold-start seconds, current only | `dev/ledger.toml` | `[timing].full_cold_seconds`, `[[hot]]` per module, `[[tree_cost]]` per subtree |
| the route flowchart | `dev/LEDGER.md`'s "Which route, under which condition" section | it is already a mermaid `flowchart TD` block. **Lift it verbatim**; a parallel dispatch may move it out of that file, so read it defensively and fall back to a clear "not found" panel rather than crashing |
| code hierarchy, and where we are | `dev/PLAN.md` section 11 | the MASTER status table, 96 rows of `\| code \| goal \| status \|`, dotted-decimal codes that give the tree; plus the Task index, 112 rows |
| the workbench: dispatched, queued, conditions | see below | |

**The workbench panel is the one with no clean source, and you must not invent
one.** The live dispatch state lives in `.claude/`, which is never committed
and which agents must not touch. So:

- read what you legitimately can: the Task index's most recent rows and their
  verdicts, and `_build/briefs/*.md` mtimes and title lines;
- for "what is dispatched now", if the data does not support it, **say so on
  the panel** rather than guessing. A dashboard that shows a stale "currently
  running" is worse than one that says "not available from committed data".
- for "what condition triggers what", the flowchart's lever branch already
  encodes it, and `dev/ledger.toml`'s `[[lever]]` rows carry each option's
  status, cost, net and risk. That is a real table and it is the honest
  content for this panel.

## WHAT THE PAGE MUST BE

- **Self-contained**: one HTML file, no external CSS, no CDN, no fonts, no
  network. Inline everything. The owner opens it from disk.
- **Mermaid**: it must render the flowchart. Since you cannot fetch a CDN,
  either inline a renderer you vendor, or emit the mermaid source in a
  `<pre>` block clearly labelled, and say which you chose and why. **Do not
  add a network dependency.**
- **Readable at a glance**: this is the owner's orientation surface, not a
  report. Numbers large, categories separated, no walls of prose.
- **Honest about staleness**: every panel carries the source it came from and
  the mtime of that source, so a stale panel is visible rather than
  misleading.

## WHAT MAKES THE UPDATE MECHANISM REAL

Add `scripts/check-dashboard.py` or a subcheck in the existing
`scripts/check-dev-docs.py`: **`_build/dashboard.html` is stale if any of its
sources is newer than it.** It is informational rather than gate-failing,
because `_build/` is git-ignored and a fresh clone has no dashboard: a gate
that fails on a missing generated file would block every new clone.

Report the exact line for the orchestrator to add to
`dev/ORCHESTRATION.md`'s return checklist. **Do not edit that file**: a
parallel dispatch is rewriting the `dev/` documents right now.
