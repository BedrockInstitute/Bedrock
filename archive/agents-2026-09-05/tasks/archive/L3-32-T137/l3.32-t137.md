### How to attribute a row, and what to do when you cannot

Read each row's `title`, `detail`, `gate` and `provenance`. Then read the
route in `dev/PLAN.md` section 3 and the `[[owed]]` rows, which already carry
the field.

**Attribute a row `BOTH` when it is genuinely shared, and also when you are
unsure.** That is the same rule the module split already uses for an ambiguous
module. `[T135]` set it and the owner accepted it.

**Do not guess a row into `AC` or `GCH` to make a number look tidy.** A wrong
`AC` makes the AC endpoint too big; a wrong `GCH` makes it too small. `BOTH`
is wrong in a stated direction, which a reader can correct.

**List every row you called `BOTH` because you were unsure**, apart from the
rows that are plainly shared. That list is the honest edge of this caliber.

## THE ARITHMETIC, WHICH HAS ONE TRAP

```
AC endpoint     = AC standing     + rows marked AC   + rows marked BOTH
GCH endpoint    = GCH standing    + rows marked GCH  + rows marked BOTH
AC+GCH endpoint = AC+GCH standing + every row
```

**The trap: the three columns do not add up, and they must not.** AC standing
and GCH standing both count the base and the shared parts, so
`AC + GCH > AC and GCH`. That is correct, not a bug. **Say so on the board**,
or the first reader will report it as one.

Assert the one identity that must hold: the AC-and-GCH column equals the
figures `ledger.py --brief` already prints. If it does not, you broke
something.
