## GOAL

This project's rules live in several documents, and D24 says each must name its
enforcement point: **a rule that is not machine-enforced must say which gate,
which brief section, or which review step enforces it, and a rule with no
enforcement point is a wish.** Several rules currently name "review" or "the
orchestrator", which in practice has meant the rule is obeyed until a busy turn.

**Survey the rule surface and say, rule by rule, which ones can be tooled
CLEANLY, and which ones must stay as documentation.**

## THE CENTRAL WARNING, WHICH OUTRANKS PRODUCTIVITY HERE

**Do not force a gate that does not have clean logic.** A gate with a bad
false-positive rate is worse than no gate: it trains everyone to reach for
`git commit --no-verify`, and once that reflex exists the good gates stop
working too. The same goes for a check so vague it fires on legitimate content,
or one whose fix instruction is "think about it".

So **"leave this one as documentation discipline" is a first-class, expected,
and respected answer**, and a report that recommends tooling everything will be
returned. The owner asked for this warning by name. Expect a substantial share
of the rule surface to be correctly untoolable: rules about judgment (is this
the ideal form? is this term the right rendering? is this the widest unmeasured
term?) generally cannot be gated, only prompted.

A recommendation of NO is as valuable as a YES here, and cheaper to be right
about.

## THE BAR A "YES" MUST CLEAR

For a rule to be recommended for tooling, all four:

1. **A decidable predicate.** State it precisely. If you cannot write the
   predicate in one sentence without the words "appropriate", "reasonable" or
   "should", it is not decidable.
2. **A measured false-positive rate.** **Prototype the check and RUN IT over
   the real tree**, then classify every hit by hand as TRUE (a real violation)
   or FALSE (legitimate content the check misreads). Report the counts. **A
   proposal without a measured hit count on the real corpus is not a proposal
   and will be ranked below the ones that have it.**
3. **An actionable failure message.** What exactly does the author type to fix
   it? If the fix is a judgment call, the check should at most WARN, never
   fail a gate.
4. **A home and a trigger.** Which gate does it run in (`make check`, the
   pre-commit hook, a dispatch-time check, a return-audit check), and why that
   one. A slow check does not belong in the hook; a check that needs the whole
   tree does not belong on staged files.

Prefer, in this order: (a) extending an existing script over adding a new one;
(b) a WARN-only advisory over a hard failure; (c) documentation over a
borderline gate.

   hard gate would not, with the reason for the split.
5. **Gaps in the existing tools**: rules the current scripts claim to enforce
   but do not fully, or enforce more strictly than the document says. A
   mismatch in either direction is a finding.
6. **What you prototyped**, with the commands you ran and their raw output, so
   every hit count can be re-derived by the orchestrator.
