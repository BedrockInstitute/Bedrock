## 4. The negative controls, and one of them refutes section 6.1

Two wrong IDs fail in two different places.

**`claude-haiku-5` fails inside the client.** The CLI prints
`[claude-code:unrecognized_model] {"model":"claude-haiku-5","query_source":"sdk"}`
and returns `is_error: true` with zero tokens. No API call is made.

**`claude-opus-5-20260101` passes the client and fails at the API.** The CLI
returns `is_error: true` and `api_error_status: 404`. The result text reads
`There's an issue with the selected model (claude-opus-5-20260101).`

**And a wrong ID in a PANE looks like a healthy run.** This is the finding that
matters. `herdr agent start` returned `agent_started` with
`interactive_ready: true` for `claude-haiku-5`. The agent then reached
`working` and then `done`. Evidence: `scratchpad/b4-b4-bad.log:4-8`.

**The banner prints the raw string when the ID does not resolve.** A resolving
ID prints a display name and never prints its own ID. A failing ID prints its
own ID verbatim:

```
▝▜█████▛▘  claude-haiku-5 with max effort · Claude Max
```

Compare the good case at `scratchpad/b4-b4-opus.log:12`:

```
▝▜█████▛▘  Opus 5 with max effort · Claude Max
```

**So the read-back refusal at `dev/memos/L9-pod-program-design.md:1667-1672` is
inverted.** Its text reads: "A pane that does not name the model it asked for
returns NO PID." A correct launch never names the model it asked for, because
the banner shows a display name. A wrong launch always names it. That refusal
would park every correct dispatch and pass every wrong one.

**The rule the measurement supports, stated for the implementer.** Read the
banner line that ends with `· Claude Max`. Park the task when that line
contains the requested model string verbatim. The match must be case
sensitive, because `Opus 5` contains `opus` under a case-insensitive match.

The banner is the only place the pane shows the model. The failure text arrives
later and only in the answer, so it is not a launch-time signal.
