`dev/PLAN.md` section 6.0 now reads, for the rules this dispatch touches

> 4. **What gets a code:** a goal with its own success criterion (a chapter
>    cluster, a spike, a review, a piece of legislation), or a dispatched task
>    (a briefed sub-agent assignment under a parent goal). Individual lemmas
>    and modules are artifacts hanging under a code, not codes themselves.
>
> 6. **Bookkeeping:** register a code in §11 *before* starting the work; update
>    the §11 row in the same commit that changes a goal's status. New codes
>    discovered mid-work are registered immediately, not backfilled.
>    **One-time reconciliation (2026-08-06, `[T111]`):** the dispatched-task
>    codes `[T1]` through `[T110]` were created before this section recognized
>    dispatched tasks, so they are backfilled into the task index once, as a
>    closed reconciliation of existing history. This is a single exception
>    with no force as precedent: rule 6's no-backfill requirement binds every
>    future code, and the reconciliation pass is never repeated.
>
> 7. **Dispatched tasks carry extended codes.** A dispatched sub-agent task is
>    coded `L<goal>.<subgoal>-T<n>` under the parent goal it serves, for
>    example `[L3.32-T101]` under `[L3.32]`, with `n` the next free number in
>    the parent's task series. The code is written in brackets wherever the
>    task is named, exactly like a goal code, and obeys rule 3 (immutable and
>    append-only) like any other code.
>
> 8. **The task index: one row per code, rows stay short.** Every dispatched
>    task code occupies exactly ONE row in the task index in §11, added in the
>    same commit that registers the code (rule 6). A row carries the code, a
>    short title, a verdict in a few words, and a pointer to the detail;
>    nothing else. **No row may exceed 200 characters**, measured as the full
>    row line from the leading `|` to the trailing `|`.
>    `scripts/check-task-index.py` enforces both one-row-per-code and the cap.
>    The cap is sized for a one-line scannable entry: code (about 11), short
>    title (about 70), verdict (about 30) and pointer (about 50) fit inside
>    200, while the failure this rule prevents, the 12,633-token cell that hid
>    the T1-T110 verdicts, is far beyond any single line. A row that outgrows
>    the cap means the detail has not moved to `dev/JOURNAL.md` or the report,
>    where it belongs.

The cap argument, stated in the rule and repeated here because it is the
load-bearing number: a one-line index entry must fit four fields, the code
(11 characters for `L3.32-T110`), a short title (about 70), a verdict token
(about 30) and a pointer (about 50). That sums to about 160 before the pipe
separators, so 200 gives headroom without ever holding a second sentence.
The failure being prevented is a cell of 12,633 tokens, about 50,000
characters, which is 250 times the cap and cannot fit on any terminal line.
The measured spread of the delivered rows, 65 to 117 characters, confirms the
fields fit comfortably (command: the row-length audit in this dispatch, max
117).

## 4. The checker and what was tuned

`scripts/check-task-index.py` enforces two rules: every code cited anywhere
in `dev/`, `_build/briefs/` or `git log --oneline --all` has exactly one row
in the task index, and no row exceeds 200 characters. Regression tests at
`scripts/tests/test_task_index.py` (14 checks) pin the extraction.

What a first draft flagged, and the tuning that killed each false positive:

1. **Bare `T<n>` cried wolf on prose.** A bracket-less regex found 467 hits
   outside any bracket in the scanned sources, including `T0`, which is a
   function variable in a literature memo, `T0 = ∅; T(ν+1) = T(Tν)`
   (`dev/literature/rudimentary-functions.md:226`), not a task code. Tuned:
   only bracket-enclosed tokens count, `[L3.32-T<n>]` (full form) and
   `[T<n>]` (the short form used across dev/ and the briefs). Every one of
   the 279 `[T<n>]` tokens in `dev/` was then verified to be a genuine task
   reference (all resolve to 1..111), so the bracket rule has no false
   positives on this tree.
2. **Prose shapes from the earlier rule-id trap.** `T-function`, `I-ideal`,
   `D-bucket` and similar capital-hyphen prose never match the digit-only,
   bracket-only regexes; pinned by tests 1 and 2.
3. **Stray table rows.** The row parser reads only the `### Task index`
   section of PLAN, so a `| L3.32-T... |` row anywhere else in the document
   (the master table has none, but the parser is immune anyway) is not an
   index row. Pinned by test "rows outside the section ignored".
4. **Zero padding.** `[L3.32-T01]` resolves to the same code as `[L3.32-T1]`;
   none exists today, but the behavior is documented and pinned.

Run against the real tree: `task index OK: 111 cited codes, 111 unique rows,
all within 200 characters`, exit 0; tests 14/14. The longest row is 117
characters, so the cap has headroom today and bites only when a verdict
paragraph tries to come back.

## 5. The rule 6 tension, resolved

Rule 6 says registration happens before starting and is never backfilled, and
110 codes already exist. The resolution is written into the rule itself, as a
single closed exception: the backfill is legitimate because it is a one-time
reconciliation of existing history, not a new habit. It is bounded in three
ways that make it unrepeatable: it names the exact codes it covers (`[T1]`
through `[T110]`), it names the exact date and task that performed it
(2026-08-06, `[T111]`), and it states in the rule text that it "has no force
as precedent" and that "the reconciliation pass is never repeated." Every
future code must follow rule 6, register in §11 before starting, and add its
index row in the same commit. `scripts/check-task-index.py` makes the
forward direction mechanical: a code cited anywhere without a row fails the
gate, so the reconciliation cannot quietly recur.
