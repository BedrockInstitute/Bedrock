## 3. The generic question, answered explicitly (D29)

The build was dispatched with the default: write it structure-generic. It
is. The machinery is module-parameterized at full strength:

- `PowerStep` is parameterized by `(σ : S) (oσ : IsOrd σ) (t : Tally (Lset σ))` ([Finite.lagda.md:330](/Users/alsg/Agentic/Bedrock/src/L/Rud/Finite.lagda.md:330)): any ordinal, any tally, no `ω`.
- `Search` is parameterized by `(A : Type) (_≺_) (tri) (irr) (trans)` (:448): any type and any trichotomous relation.
- `Sside` is parameterized by `(u : S) (t : Tally u)` (:589): a tally of any set yields one of its step.
- `Power` is parameterized by `(k : ℕ) (C∈J : ...) (tally : Tally (Lset (IS.# k)))` (:971): the obligation reads over any finiteness evidence of the carrier.
- `ltally`, `sTally`, the masks, `select`, `marks`, and the decide trio carry no `ω` at all.

The only fixed block is the first-limit one (`limω`, `∅∈Ssetω`,
`baseStage∈J`, `op-in-J`, `finSetMem`, `Power`'s ω-level assembly), and there
the fixity is essential, not expedient: the finiteness of a constructible
stage `Lset ζ` for `ζ ∈ ω` is exactly the numeral case, and at a general
limit `α` the statement is false (a member `ζ ∈ α` can itself be a limit,
with `Lset ζ` infinite). The generic-over-`α` version of `finSetMem`/`Power`
would add closure parameters for a second consumer that does not exist, so
the instances are stated at `ω` over the generic machinery, which is the
D29 answer: generic at full strength where the content is generic, fixed
only where the mathematics is the numerals.

One shape change to the delivered code is worth recording: the local proof
helpers of `select-out`/`select-in`/`part-out`/`part-mask` were renamed
`step` -> `go` because the chapter imports `L.Rud.Step`'s `step`, and a local
`where` binder named `step` would clash (wall class below).

## 6. Walls, by LESSONS class

- **Naming collision (constructor vs. binder), measured twice.** Importing
  `L.WellOrder.Base`'s `eq` (`Tri`'s middle constructor) turns a `where`
  binder named `eq` into a constructor pattern: `ω-not-zero eq = ...`
  failed with `SplitError.NotADatatype` ("Cannot split on argument of
  non-datatype `IS.ω ≡ ∅`") and cost one bisect against the import set
  (isolated to the `eq` name; the isolated file with the same imports
  reproduced it, and renaming the binder to `e` cleared it). The delivered
  `L.Rud.BaseBlock` never hit this because it does not import
  `L.WellOrder.Base`. Same for the local `step` helpers once `L.Rud.Step`'s
  `step` is imported (clash on definition, fixed by renaming to `go`).
  **Proposed as a new LESSONS entry (C-series, awaiting owner ID):** a
  binder that shares its name with an imported constructor is a parsing
  trap; when a chapter imports a module whose constructors are short
  words (`eq`, `lt`, `gt`), no where-binder may reuse them, and a
  `SplitError.NotADatatype` naming the binder's *type* is the symptom to
  recognize.
- **Module parameters are not fields (Agda 2.8.0), measured.** `module N = M a`
  does not make `N.x` accessible for a parameter `x` of `M`; only
  definitions inside `M` are fields. The delivered `Power` exposed its tally
  as a definition (`t = go (stageOrder k)`), so `P.t` worked; restating the
  tally as a module parameter broke `P.t` with `NotInScope`. Fixed by keeping
  the tally as the parameter `tally` and re-exposing `t = tally` as a
  definition ([Finite.lagda.md:971-978](/Users/alsg/Agentic/Bedrock/src/L/Rud/Finite.lagda.md:971)). Not a LESSONS-class wall so far as the book's
  experience goes; recorded here as a datum.
- No conversion wall, no termination issue, no inference trap surfaced in
  the build; the delivered bodies typechecked at their delivered speed.
