# [L3.32-T119] Adversarial review of the dispatch mechanism: what the eighteen do not cover

tier: codex (adversarial review; the critic built none of this)

Every line number refers to `.claude/skills/codex-dispatch/dispatch.py` unless
another file is named. This review was performed from a workspace-write
sandbox in which `ps` raises EPERM; that environment is used below as a live
demonstration, not as a hypothetical.

## 1. The failures still uncovered, ranked by expected cost

### 1.1 A live agent reads as dead when `ps` is unreadable, and the fix that claimed to prevent this now produces it

Shape: D2 (live agent read as exited) re-entered through a different branch,
with the D12 warning discipline absent at the point that matters.

`alive()` (138-164) answers False when the PID's start time cannot be read:

```
if started:
    now = proc_start(pid)
    ...
    if not now:
        # D1 (T73): ... Unverifiable is not alive.
        return False
```

`proc_start()` (128-136) swallows the OSError and returns "". So in any
environment where `ps` is blocked, every record with a stored start time reads
as dead. This is not a hypothetical. In this review sandbox `ps` raises
PermissionError (verified with `subprocess.run(["ps", "-o", "lstart=", "-p",
"3377"])`), and `dispatch.py status` reports `agents live: 0` and flags T119,
the reviewing agent itself, as `EXITED WITH NO FINAL MESSAGE` while its log was
written nine seconds earlier. `dispatch.py gate-ready` then exits 0 with `no
agent is live; a full-tree gate will read a settled tree` while T119 is
mid-write.

That is failure mode 8's spurious GREEN, produced by the very mechanism that
fix 8 added, and it is worse than the disease it fixed: the D1/T73 branch was
changed so a dead agent cannot hold a slot, and the mirror image (a live agent
freeing its slot, disarming gate-ready, enabling a duplicate `resume`, and
letting `wait` announce a running agent as returned) is silent. The tool's own
D12 precedent says an unreadable `ps` must be a WARNING, not an all-clear
(180-225); `alive()` has no warning channel and `running()` (171-174) and
`gate-ready` (815-833) consume its silent answer.

### 1.2 Corrupt registry: recovery throws away the live set and disarms the gate block and the slot ceiling

Shape: number 8's gate block and number 2's slot accounting both depend on the
registry, and the registry's corruption path resets it silently.

`load()` (101-119) moves a corrupt registry aside and returns a fresh empty
one, printing to stderr that live agents are "still running: recover their
records from that file or re-adopt them". There is no re-adopt command anywhere
in the tool. Every live agent is now unregistered: `gate-ready` authorizes a
gate over half-written masters, the Agda slot count drops to zero so a third
and fourth agent can launch, and `wait` prints `nothing is running`. `status`
is the only partial backstop (`strays()` would flag the orphans as unmanaged,
180-225), but `gate-ready` does not call `strays()`. The D12 lesson (an
unreadable sensor must refuse, never clear) is applied to `ps` but not to the
registry read.

### 1.3 The recommended notification path (`run --wait`) consumes the report without writing the durable log

Shape: number 11 (a return consumed with no recoverable record), through the
very route the skill now recommends instead of arming.

The durable log is written in exactly one place, `cmd_wait` (786-795). The
`run --wait` path (`_wait_for`, 431-459) sets `reported = True` under the lock
but never appends to `returns.log`. SKILL.md (32-33) calls `run --wait` "the
whole notification path" and tells the orchestrator to run it as a
harness-tracked background job. If that command's output is discarded (the
number 11 shape: backgrounded inside a compound command, printing into a pipe
nobody reads), its exit is invisible, the return is marked reported, and
`already_announced()` (640-657) never sees it because the durable log has no
line. The number 11 fix therefore covers the old arming shape and not its own
replacement.

The registry supplies corroborating forensics: T97 and T98 are `reported =
True` with final messages on disk, yet `returns.log` contains no T97 or T98
line at all (verified with `rg -c` and a registry read), while the log covers
T96 and everything from T99 onward. At least one report path consumed those
returns without writing the durable log. The current `_wait_for` is exactly
that path.

### 1.4 `already_announced()` keys on task name, so a re-dispatched task under a recycled name is treated as old news

Shape: number 10's detector over-corrected and now produces the failure it was
written to prevent, for re-dispatches.

`already_announced()` parses `returns.log` and returns task NAMES (642-656).
`cmd_wait` drops every watched task whose name appears (723-729) and, if none
remain, prints `nothing new to wait for` and exits without arming (730-734).
The project re-runs task codes by design: `launch()` keeps superseded records
in `history` for exactly this reason (331-333), and the 200-character row cap
in `check-task-index.py` (26-29) forces one row per dispatch, not per code. A
waiter armed after `run T` re-dispatches T sees T in the durable log from the
previous generation, decides there is nothing to wait for, and exits. The new
agent's return is unwatched, recreating the 52-minute failure with the fix
itself as the cause. The durable log needs record identity (task plus session
or pid), not just the task name.

### 1.5 The singleton has no harness check; the comment says it exists

Shape: numbers 2 and 11 together. The stated design intent is not implemented.

The comment at 714-718 says "Retiring the stale ones runs AFTER the harness
check below ... A read-only call must not disarm the mechanism it is
inspecting." The code between that comment and the kill loop (720-733) contains
only the `already_announced()` handling. There is no harness check anywhere in
`cmd_wait` (verified by reading 685-812 and grepping for `harness`, which
appears only in docstrings and comments). Every invocation of `wait`, including
an inline `wait --timeout 10` peek or a `wait` whose output the harness will
not track, first SIGTERMs the on-duty waiter (734-745) and then watches. If the
new caller's output is lost, the notification path is down with nobody
watching, which is precisely the incident that number 11's fix was supposed to
end. The kill loop is also racy: two waiters arming in the same tick both read
the `pgrep` output before either exits, so each can kill the other, leaving
zero waiters (the mirror of number 2's five).

### 1.6 The rule-bundle refusal derives the kind from a header that 89 of 127 real briefs lack

Shape: number 15 (a gate that can be passed with the wrong content) and the
T105 lesson quoted at 847-849 (an author who declares the kind chooses the
bundle). The fix is newer than the eighteen and is not on the list, which makes
it a live example of the rate problem: a check added the same day, already
undermined by the corpus.

`rule_bundle_defects()` (837-894) derives the kind from a `## SCOPE (write)`
section (857-858). A measured scan of `_build/briefs/` (127 files, one-line
Python) shows 38 briefs carry that header and 89 do not, including six of the
last twenty (t100, t104, t105, t109, t115, and t119 itself). With no header the
kind silently defaults to `recon` (874-875), whose bundle is the smallest in
`dev/rules.toml` (47-49: recon is D-10, C-22, P-l; probe at 43-46 adds D-1,
P-i, C-12; build at 39-42 adds P-h, P-k, R-35, R-36, R-38, I-4, I-5). A probe
or build brief without the
header is therefore checked against the recon bundle: D-1 (probes are never
committed) and C-12 (heap cap) are not demanded. The validator never requires
the header at all, even though ORCHESTRATION section 3 says every brief
carries `SCOPE (write)`.

Verified live: `dispatch.py check` refuses the real, delivered build brief
t101 for five missing build laws (P-h, R-36, R-38, I-4, I-5), while the probe
brief t50 is classified `recon` and only checked for P-l. t50's write scope is
declared in prose mid-brief (`src/ProbeW3Seq.agda`, l3.32-t50-brief.md:82)
with no `SCOPE (write)` header at all.

### 1.7 Queue then resume double-launches the same brief under two task names

Shape: number 13 (two live dispatches claiming the same write territory),
reached through a hole in the collision check that was supposed to prevent
double-launching.

`launch()` refuses a task already in `running()` (344-347) and `cmd_queue`
checks the same name (498-500), but `cmd_resume` launches under
`{task}-resume` (558-560). Sequence: T is dispatched, dies; `queue T` arms a
detached waiter that sleeps for an Agda slot; the orchestrator instead resumes
T, creating the live record T-resume; the queue waiter wakes, checks `running`
for T (absent, since T's record is dead), and launches T. Two live agents,
same brief, same write territory, no check anywhere. The registry already
contains T53-resume and T81-resume records, so the naming path is in active
use.

### 1.8 The Agda slot ceiling is stale relative to C-12, three documents disagree, and nothing stops two profiles from corrupting each other

Shape: number 17's corrupted measurements and number 8's concurrent-write
hazard, on the campaign's currency.

The dispatcher hardcodes `AGDA_SLOTS = 2` and `-M8g` (77-78) with a comment
citing C-12 as "at most two concurrent". LESSONS.md C-12 (1778-1806) now says
up to FOUR concurrent writers at `-M8g` in WIDE mode and TWO at `-M12g` in
HEAVY, with the third and fourth slots gated on free memory above 25 percent
and a watchdog. AGENTS.md says agent Agda runs "one process at a time". Three
documents, three ceilings; the tool implements none of the memory floor, the
tier, or the watchdog. The prompt's own direction ("what else must not run
concurrently") names the real hazard: two `agda --profile=definitions` runs on
the same module produce two measurements that both corrupt each other, and the
campaign funds decisions on those numbers. Nothing in the dispatcher knows
what module an agent profiles, so the two-slot ceiling is the only guard and it
allows the case that matters.

### 1.9 `gate-ready`'s own recovery advice is impossible in the state it refuses in

`cmd_gate_ready` (815-833) prints "Wait with `dispatch.py wait --all`".
`cmd_wait` refuses `--all` whenever more than one agent is live (705-712),
which is exactly the state `gate-ready` refuses in. With two agents the advice
cannot be followed; the working recovery is repeated plain `wait` and re-arm.
The refusal also happens before `already_announced()` pops already-reported
tasks (723-729), so `wait --all` refuses in a state that would be legal after
the pop. Both are small, but a fix whose suggested recovery is a dead end is
the same shape as number 8's advice-as-enforcement failure.

### 1.10 `waiter_alive()` still detects waiters by command-line pattern

Shape: number 6 (pattern matching counted the watcher itself), one level up.
The slot counter was moved to explicit registry PIDs (176-178, 344-347), but
`waiter_alive()` (659-665) and the singleton kill loop (734-745) still use
`pgrep -f "dispatch.py wait"`, excluding only `me` and `os.getppid()`. Any
process whose command line contains that string (a shell running the command
in a compound, an editor buffer of the file, a wrapper) suppresses the NO
WAITER banner or gets killed as a "stale" waiter. The incident list fixed the
pattern-match for slots and left the same shape in place for the alarm and the
singleton.

## 2. D-10 spot-check

Three items verified against the code, chosen to cover the list's strongest
claims.

**Item 1 (`wait --all` refuses).** Verified: `cmd_wait` refuses with exit 2
when `len(watched) > 1` (705-712), and `watched` is the live set from the
registry (693). The mechanism is real. Two caveats, both in section 1: the
refusal runs before the `already_announced()` pop (1.4), and `gate-ready`'s
advice contradicts it (1.9). The incident's own forensic record partially
survives: T97 and T98 were dispatched 09:42:41/42 and carry `reported = True`
with final messages, while `returns.log` shows T96 at 10:16:24 and nothing for
T97/T98, consistent with returns consumed by a report path that never wrote
the durable log (section 1.3).

**Item 3 (model block in `launch()`).** Verified: `check_model` (227-240) is
called from `launch()` (311-314), from `cmd_run` (464-467), and from
`cmd_queue` (490-493); `resume` passes through `launch()` so it is covered too.
The date gate (73) lifts itself after 2026-09-01 and `--allow-model` exists as
an explicit escape. Honest as described.

**Item 8 (`gate-ready` refuses while agents are live).** Verified: the command
exists (815-833) and refuses when `running()` is non-empty. But the sensor is
the fragile part: in this sandbox `ps` is EPERM-blocked, `running()` sees
nobody, and `gate-ready` exits 0 while the reviewing agent (T119) is mid-write.
The fix is real and its load-bearing assumption (registry liveness is
trustworthy) is not, which is section 1.1.

**Misdescriptions found.**

- Item 12 says "`run` and `status` shout when agents are live and no waiter is
  armed". Only `status` does. `warn_if_unarmed()` has exactly one call site,
  line 621 in `cmd_status`. `run` never calls it; `launch()` prints a constant
  "ARM THE NOTIFIER" line on every dispatch (418-419) regardless of whether a
  waiter is armed.
- Item 13 says the orchestrator writes "Never: X, agent Y holds it" into every
  brief. A scan of the 127 briefs finds 16 with any anti-overlap phrasing, and
  the actual form is `**Anti-overlap**: [T47] owns ...` (l3.32-t57-brief.md:113)
  or prose like "your only writes are ..." (l3.32-t50-brief.md:183). The exact
  quoted phrase appears only in this brief's problem statement. "Every brief"
  is wrong; concurrent-wave briefs carry the clause and single-agent briefs do
  not. The substance (hand-written, nothing checks it) is correct.
- Item 2's fix description: the code comment claims a harness check protects
  the on-duty waiter from inline invocations; no such check exists (section
  1.5). The stated design intent is unimplemented.

Overall the list is honest about which fixes are mechanised and which are not;
the three items checked exist as described, and the misdescriptions found are
in the fix descriptions (12, 2), not in the incident accounts. The one
systematic bias: the list describes each fix as complete, and the review's
main findings are the places where the fix is not the mechanism the comment
claims it is (1.1, 1.3, 1.5).

## 3. The three gaps

### 3.1 Write territory (13)

**What it would read.** The registry's live set (each record stores its brief
path, 385) and the `SCOPE (write)` section of each live brief. The parser
already exists in disguised form: `rule_bundle_defects` drops "never" and
"do not" lines and extracts `src/...` paths (864-868), and the read-only
validator already tokenizes the same section (267-270). The check would refuse
to launch when the new brief's write set intersects any live agent's write set
on `src/` or `dev/` paths.

**What it would refuse.** A second agent whose brief names a master or probe
file another live agent may write. It must ignore `_build/*-report.md` (the
per-task report is one-shot and unique) and `/tmp` scratch.

**The false positive that would kill it.** The corpus is not in the shape the
check needs. 89 of 127 briefs have no `SCOPE (write)` header at all, including
six of the last twenty, so a parser over that header silently passes
everything (under-refusal, which makes the check theater) or refuses briefs
whose scope is declared in prose (over-refusal, which blocks real dispatches).
123 of 127 briefs write a `_build/...-report.md`, so an intersection over
`_build/` fires on every single dispatch; the check must exclude report paths
or it is worse than useless. Probe briefs name similar files
(`src/ProbeW3Seq.agda`); worktree runs write outside the ROOT tree and must be
resolved against their own cwd, not path equality against the checkout. The
check is only buildable after the validator REQUIRES the `SCOPE (write)`
header (turning 89 prose-style briefs into a refusal until rewritten), because
a territory checker parsing free-form CONSTRAINTS prose would inherit the very
heterogeneity that makes the hand-written clauses unreliable today.

### 3.2 Asserted versus measured (14, 15)

**What it would read.** Two narrow inputs: the return text (the report in
`_build/`) and the register entry the orchestrator writes in `dev/PLAN.md`
section 11.

**What it would refuse.** A register row whose verdict contains "overturn",
"refuted", or "restored" when the cited report contains an explicit
no-measurement admission ("typechecked nothing", "ran no Agda", "no command
run"). The hook is the incident's own honesty: T104 said it had typechecked
nothing, and the failure was not the recon, it was the register entry written
as a verdict (LESSONS.md P-l entry, 2000-2012, records the same). A second,
cheaper rule already exists in the return-audit checklist: a return that
changes a TECHNIQUE must carry the measurement (ORCHESTRATION 209-227, and the
seconds requirement at 220-221). Extend the same rule to verdicts: a register
entry that overturns a prior verdict must cite a command, or the entry may only
record a hypothesis. `check-task-index.py` already reads PLAN rows and the
report corpus; this is the same shape of checker with a verdict trigger.

**The false positive that would kill it.** Requiring every claim in every
brief and every finding in every return to carry a "measured:" or "reasoned:"
label. The corpus shows prose claims are unmarked everywhere, so the gate
would refuse most briefs until authors inserted labels to satisfy it, and a
label nobody reads is a ritual (the magic-string problem the evidence check
already hit at 287-293). Recons that synthesize prose legitimately run
nothing; the marker must be triggered by an overturn verdict, not by absence
of measurement. Keeping the trigger on register verdicts plus the honest
admission is what keeps the false-positive rate low: the failure mode it stops
is specifically the "recorded as a finding before any measurement" shape.

### 3.3 Arming (11, 12)

**Mechanism one: make arming unnecessary.** The tool already has the shape:
`run --wait` blocks and reports in one command (461-474) and SKILL.md makes it
the primary path (32-33). Two holes found in this review: (a) `queue` also
accepts `--wait` (the flag is added by `common()`, 921-925, to both `run` and
`queue`) but `cmd_queue` never reads it, so `queue --wait` is a silent no-op,
an accepted flag that does nothing; and (b) `_wait_for` never writes the
durable log (section 1.3). Making arming unnecessary means closing those two:
either refuse `--wait` on `queue` (a silent no-op is worse than a refusal) and
append to `returns.log` in `_wait_for`.

**Mechanism two: make recovery cheaper.** Recovery already exists (durable
log, status banner, silent-return list at 593-601). The two gaps are sections
1.3 and 1.5. The singleton should stop killing and start refusing: register
the waiter in the registry (one row, pid plus start time, reusing `alive()`'s
recycling check), and have a new `wait` refuse while a live waiter is
registered, with an explicit `--force` to replace it. That removes the
mutual-kill race, removes the pgrep pattern (1.10), and makes an inline peek
refuse instead of disarming the on-duty waiter. The false positive that would
kill it: a waiter that died without clearing its row. `alive()` already
handles that with the PID recycling check, so the stale row is detected the
same way dead agents are. The refused case (a second `wait` while one is
armed) is exactly the case the tool should refuse, and `status` exists for
peeking.

## 4. The fixes I judge wrong

**Number 18's detector: removal was right, and I would not rebuild it.** A
check that cannot separate the failure from the correct usage (stdout is a
pipe in both the harness-tracked case and the lost case, per the code comment
627-637) fires on the correct case and trains the operator to ignore it.
Removing it was the correct call. What was not completed is the replacement:
the durable log does not cover `run --wait` (1.3) and the singleton's claimed
harness check does not exist (1.5). The removal is not the problem; the
incomplete substitute is.

**Number 12's warning: by this project's own standard it is a wish, and the
codebase says so about the same shape.** The rule-bundle comment (838-849)
argues that a sentence in ORCHESTRATION whose enforcement point is the
orchestrator's intention is a wish, and `warn_if_unarmed` (667-683) is exactly
such a sentence: it prints, and the enforcement point is the orchestrator
reading it. The fix direction is right (make arming unnecessary via
`run --wait`), but as implemented it is not enforcement. The gap is not the
warning's weakness, it is that the stronger path has the two holes in section
3.3.

**Worse than the disease: `alive()`'s "unverifiable is not alive" (158-163).**
This is my pick for the over-fitted fix. It was written to stop a dead agent
from holding a slot (the comment names T73), and it chose silent False for the
unreadable case, which recreated the original D2 failure (live reads as dead)
on the `ps`-unreadable axis. It is load-bearing for the slot ceiling, the gate
block, the resume refusal, the wait report, and the status alarm, and it has no
warning channel, unlike `strays()` which the same session fixed by warning and
refusing (180-225). A mechanism that is only correct when its sensor works,
and that cannot tell you the sensor is broken, is worse than the defect it
replaced, because the defect was at least visible in `status` before the
change.

**Over-fitted: the singleton's kill loop (734-745).** Fitted to the
five-stacked-waiters incident, it solves "too many waiters" by SIGTERM and
leaves the "zero waiters" case open (1.5), including the mutual-kill race and
the inline-peek disarm. The `wait --all` refusal (705-712) is a smaller
instance of the same over-fit: it refuses before applying its own
already-announced filter.

## 5. What I would not build

1. **A territory collision detector against free-form brief prose.** Not until
   the `SCOPE (write)` header is required and the 89 headerless briefs are
   rewritten. Building the intersection check now produces either a silent
   pass (under-refusal) or a gate that fires on report paths and `/tmp`
   (over-refusal), and eighteen fixes in a day is a rate at which a false
   gate is a real cost. The prerequisite is one validator line; the check
   itself is then small.
2. **A "measured:"/"reasoned:" label requirement on every brief claim and
   every return finding.** It would not survive contact: the corpus is
   unmarked, authors would insert labels to pass the parser, and a label
   nobody reads is a ritual. The verdict-triggered register check (3.2) gets
   the same protection at the point where the damage happens.
3. **A live model-availability probe at every dispatch.** The date gate plus
   the documented one-line recheck (227-240, SKILL.md 99-105) is the right
   shape; a network dependency in the launch path trades a known, dated block
   for a new failure mode (dispatch refused or delayed when the catalog is
   unreachable), which is the same class of silent wrongness the review is
   about.
4. **The fcntl/stdout arming detector, in any version.** Section 1.5's
   registry-based singleton refuses instead of detecting, and section 3.3's
   `run --wait` repair removes the step. A detector that guesses where its
   stdout goes is the number 18 lesson, and the lesson was correct.
5. **A persistent supervisor daemon that owns agents and waits forever.**
   It recreates the process-group ownership that killed two agents (number 5)
   and re-introduces a singleton with a crash-stale state. The single-shot
   wait plus the durable log plus the status alarm is the right architecture;
   what needs work is the two holes in the current single-shot paths (1.3,
   1.5), not a new long-lived process.

## What would I build first

In order: (1) make `alive()` refuse or warn when `ps` is unreadable instead of
answering False, so `gate-ready` cannot authorize a gate over a live agent
(section 1.1); (2) append every report path, including `_wait_for`, to
`returns.log`, and add session identity to `already_announced()` (1.3, 1.4);
(3) registry-based singleton that refuses a second waiter instead of killing
the first (1.5); (4) refuse `queue --wait` until it is implemented, or
implement it (3.3). Each is small, each removes a failure the eighteen list
claims to have fixed, and none of them adds a new state file or a new process.
