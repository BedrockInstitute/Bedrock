## 1. The D-10 truth check: the target is TRUE at the delivered syntax

The check rests on four facts, each verified before the proof was priced:

1. **The syntax is a plain inductive family.** `Term` and `Formula` are
   ordinary `data` declarations with finite constructor sets (two and twelve;
   `src/FOL/Syntax.lagda.md` lines 42-45 and 94-105), no truncation, no
   HIT, no infinitary branching. A formula is a finite tree.
2. **The constant domain is empty.** The target's type is `Formula (⊥* {ℓ}) k`
   with `⊥*` the empty type (`Cubical.Data.Empty.Base`, `⊥* = Lift ⊥`), so
   `Term (⊥* {ℓ}) k` is just `Fin k` (the `con` constructor is uninhabited),
   and the only leaves are de Bruijn variables.
3. **`Fin k ↪ ℕ` is delivered.** `toℕ` with `inj-toℕ`
   (`Cubical.Data.FinData(.Properties)`) gives it, and the probe uses it
   (`tcode`, `tcode-inj`, `ProbeShapeCount.agda` lines 109-115).
4. **An injective pairing on ℕ exists constructively.** `pair a b =
   (a+b)² + a` lies in the disjoint level intervals `[s², s²+s]` for
   `s = a+b`; injectivity is proved from the delivered `≤-·k`/`<-·sk`
   (`ProbeShapeCount.agda` lines 63-104). This is the one piece of raw
   material the tree lacked: `V.Coding`'s pairing is Kuratowski on the
   hierarchy's sets (`src/V/Coding.lagda.md` lines 138-187), and no ℕ
   pairing exists anywhere in the cubical library in use.

The boundary of the truth check is exactly the word "constant-free": with a
nonempty constant domain `K`, `Formula K k` is as large as `K` and need not be
countable; the empty domain is what makes the tree finitely branching. There
is no universe-level obstruction: the injection is a function at the formula
type's own level `ℓ` and the proof is generic in `ℓ` (`module
ProbeShapeCount {ℓ : Level}`). The statement is per-arity, and per-arity is
precisely what the consumer needs: `ProbeCard.step3` feeds `shape↪ k φ` into
`TupleCode.tup (suc k)`, where the arity `k` is carried separately by the
tuple's length marker, so no global code on `Σ[ k ] Formula (⊥* {ℓ}) k` is
required (`src/ProbeCard.agda` lines 649-654).

## 2. The probe: a transplant plus one new pairing

The code is the tagged-pair code of `FOL.Coding` (`src/FOL/Coding.lagda.md`
lines 310-400), with the set carrier `S` replaced by `ℕ`: constructor tags
0..11, payloads the codes of the parts, terms coded by `toℕ`. Injectivity
uses the tree's own trick from the "codes determine formulas" section, which
computes the constructor from the tag instead of writing the 144-case grid:
`tagOf`/`payOf`/`shape`/`Match`/`matches`/`go`, twelve clauses each
(`ProbeShapeCount.agda` lines 133-237). The packaged target is `T17` (lines
244-246): `Σ[ f ∈ ((k : ℕ) → Formula (⊥* {ℓ}) k → ℕ) ] (∀ {k} {φ ψ} → f k φ
≡ f k ψ → φ ≡ ψ)`.

Measured size: **197 code lines** (non-comment, non-blank; 275 file lines)
against the 250-line stop-line. Cold check 0.9 s user (1.37 s wall including
startup); warm checks 0.65 s. The arithmetic (`pair`, `≤+`, `ss+1`, `sq-lt`,
the two chains, `sq-lemma`, `pair-inj`) is ~25 of those lines (the pairing
section, lines 58-104); everything else is the transplant, shortened by the
empty constant domain (the term layer is one real clause plus two empty
cases, against the four clauses `FOL.Coding` needs).

Two engineering notes. First, the module takes no `LEM` parameter (the T9
probe carried one unused); the count is fully constructive. Second, the one
unification failure during development, `pair-inj`'s implicit arguments, is
the I-4 family: Agda cannot invert the arguments of a *defined* pairing from
an equation between its values (it emitted the 14-constraint blast of
`(a+b)² + a`-shaped metas). The delivered `pr-inj` never hit this because its
`pr` is an abstract module parameter. The cure is explicit arguments at every
call site; it was an immediate, local fix with no normalization cost, so not
a wall by the law's measure.

## 3. Subroutine, not a chapter

The shape-count is a subroutine: 197 lines, of which ~155 are a direct
transplant of a delivered, typechecked pattern and ~42 are the one new
arithmetic fact. Contrast with T1's 448 code lines (`_build/l3.32-t9-report.md`
section 2): T1 needed a decode and a full reconstruction round trip at a
concrete shape; the shape-count needs only injectivity, which the `Match`
computation supplies without ever normalizing code values. A *chapter* in
this tree's ledger (for comparison) is the ordinal-pairing theorem, 250-400
lines of genuinely new ordinal mathematics (T9 section 3); nothing here is
in that class.

## 4. Landing in an infinite ordinal's index

The numerals' injection is delivered: `V.Coding.#-inj′` (`src/V/Coding.lagda.md`
line 114) proves distinct numerals are distinct sets, and the fiber-based
`nat↪ : ℕ → ⟪ α ⟫` into any ordinal `α` with `⟨ ω ∈ˢ α ⟩` was already
typechecked in `ProbeCard.Product`. The probe re-checks it in-file
(`ProbeShapeCount.agda` lines 257-269) and composes:

```
shape↪ : (k : ℕ) → Formula (⊥* {ℓ}) k → ⟪ α ⟫
shape↪ k φ = nat↪ (code φ)

shape↪-inj : ∀ {k} {φ ψ} → shape↪ k φ ≡ shape↪ k ψ → φ ≡ ψ
```

(`ProbeShapeCount.agda` lines 271-275). This is the exact signature
`ProbeCard.step3` consumes, injectivity per arity included. What it takes to
land the count in the ordinal's index is therefore nothing beyond the probe
itself: the composition is typechecked, ~20 lines in the cardinal chapter's
definitional layer.
