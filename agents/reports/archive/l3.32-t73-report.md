## 1. Verdict

**Yes, a return can still go unannounced, and the worst idle window is unbounded: it ends
only when somebody happens to run `status` or the owner asks, which is exactly the shape of
the 52-minute incident.** Two of the paths are worse than the incident, because even the new
`status` backstop cannot see them:

1. A dead agent whose pid was recycled reads RUNNING forever whenever `ps` is unreadable
   (which is true in this sandbox, and was measured in T58's D12), so `wait` never fires
   and the `status` alarm never fires either (D1, reproduced).
2. Registry corruption or loss while agents are live makes the in-flight waiter hang
   silently forever and leaves the agents invisible to `status`; stray re-discovery is blind
   when `ps` is denied, and no re-adopt command exists (D2, reproduced).

Both proximate patches are incomplete in a specific, reproduced way. The adoption patch only
adopts agents that are still alive at a poll tick, so an agent dispatched after the waiter
starts that dies within 15 s is never watched, never announced, and never flagged (D3). The
one-shot human arming step is unchanged, `queue` does not even print the reminder (D4), and
the alarm's `started.startswith("2026")` filter is a scheduled self-destruct: from
2027-01-01 every unreported return escapes it, and records without a `started` field already
do today (D5).

The single most severe reproduced defect is the recycled-pid phantom (D1): it silently
defeats both the notification and the backstop while holding the slot and blocking `resume`.
The cheapest structural improvement is to make the dispatch command itself the harness-
tracked job that announces the return (`run --wait`: launch, then block until that agent
returns, then exit; the job exit is the notification), which removes the human re-arming step
entirely. Failing that, register live waiters in the registry and have `run`/`queue`/`resume`
refuse to dispatch when no waiter is alive, and fix D1/D5/D6 or the check can still lie.
Section 4 develops this.

## 4. The design question: can the human arming step be removed?

**Yes, there is a design that removes the dependency, and it fits both constraints.**

The constraints are: agents must stay detached (so no parent-based notification), and only
the orchestrator can create harness-tracked jobs (so `dispatch.py` cannot register a job
itself). The harness contract is per-job-end: a tracked job announces itself by exiting.
That contract is the whole problem with a persistent waiter: a waiter that never exits
announces nothing. The design that fits is to make **each dispatch command itself the
tracked job that announces its own return**:

- Add `--wait` to `run` (and `queue --wait`). The command launches the agent exactly as
  today, then instead of returning it blocks using the existing `cmd_wait` logic scoped to
  that task (or first-return), prints the return block that `cmd_wait` already produces, and
  exits 0.
- The orchestrator runs `python3 dispatch.py run T <brief> --wait` as the harness-tracked
  background job, which is already the documented way to run `wait`
  (SKILL.md:32-35). The job's exit is the notification, so there is no separate arming step
  to forget, no "re-arm after each dispatch", and no adoption gap, because the waiter starts
  in the same process that writes the registry record. Killing the job cannot kill the agent
  (`start_new_session=True`, `dispatch.py:357`), so the only cost of a killed job is the
  same lost notification that exists today, with the `status` alarm as the backstop.

**Cheapest self-correcting guard, if `--wait` is not adopted:** register every live waiter
in the registry (a `waiters` array of `{pid, started}` written under the same lock), and have
`run`/`queue`/`resume` check for a live waiter and refuse (or return a distinct exit code
with a loud warning) when none is armed. That converts the prose reminder into a checked
condition. It must be paired with three fixes or the check can still lie: the alarm's year
filter (D5), the reported-before-print ordering (D6), and the liveness check (D1), because a
dead waiter whose pid was recycled would falsely satisfy the registry check. `queue` must
also print the reminder itself (D4).

**The residual that no tool-side design can remove** is the human step of creating the
tracked job at all: under "only the orchestrator can create harness-tracked jobs", the tool
cannot spawn its own notifier. The cheapest guard for that residual is the `status` alarm,
made honest by fixing D1, D5, and D6, and made discoverable by fixing D10 so the next
dispatch surfaces it. With those three fixes, the worst remaining case is "the orchestrator
never runs `status` and never dispatches again", which no mechanism inside this constraint
set can reach.
