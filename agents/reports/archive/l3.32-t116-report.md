## 1. The route flowchart without mermaid, JavaScript or a network dependency

The mermaid path is gone. `MERMAID_FENCE` and `extract_mermaid()` were
deleted, and `route_block()` no longer returns a `flowchart TD` string. D-10
first: `route_block()` had exactly one caller, `panel_route()` (was
`scripts/dashboard.py:564`), and nothing else referenced the mermaid helpers
outside the test file, so the return-type change is contained.

The panel now builds the graph as a tree of plain dicts and renders it as
semantic HTML with inline CSS:

- `build_route()` (`scripts/dashboard.py:180`) fixes the decision structure
  in code: the campaign branch (freeze on or off, and what each answer
  releases) and the lever branch (the five questions in order). Every leaf is
  populated from the ledger's `[[lever]]` rows with the same bucket logic as
  before (refuted, in-route, superseded, gated, waiting) and the freeze note
  from the frozen `[[owed]]` rows, so a leaf changes the moment its row does.
- `render_route_node()` (`scripts/dashboard.py:315`) and `render_route()`
  (`scripts/dashboard.py:344`) emit the two branches side by side (a
  `grid-template-columns: 1fr 1fr` `.route`). Decision nodes carry a dashed
  amber border and tinted background, outcome nodes a solid border, and the
  start node a third style. An outcome that names real levers shows them as
  chips (`.leaf`); an empty lever bucket shows a muted "none" chip. Only the
  five bucket outcomes carry leaves, so the pure-label campaign outcomes show
  no chip at all (verified: 0 `class="leaves"` blocks in the campaign branch,
  5 in the lever branch, 1 "none" chip for the currently empty gated bucket).
- The one graph edge that looped (`Exit --> Freeze`) is rendered as a
  terminal "repeat" edge back to a copy of the freeze question, so the tree
  stays acyclic; `render_route_node` also carries a depth guard as a last
  resort against a future cyclic tree.
- `route_block()` (`scripts/dashboard.py:302`) now catches a missing or
  unreadable ledger and returns the no-data branch instead of crashing,
  matching the other panels.

## 2. Parsing the workbench file, and the drift fallback

The hand-written half of `panel_workbench()` is no longer dumped into one
`<pre>`. New functions:

- `WORKBENCH_HEADINGS` (`scripts/dashboard.py:849`) names the four sections;
  `match_workbench_heading()` (`scripts/dashboard.py:861`) recognizes a
  heading forgivingly (markdown markers, case, extra whitespace) and keeps
  anything that follows it on the same line.
- `split_on_arrow()` (`scripts/dashboard.py:875`) splits an item on the first
  `<-` or `->`; both sides must be non-empty, so a dangling arrow falls back
  to verbatim.
- `split_workbench_items()` (`scripts/dashboard.py:892`) scans the raw lines:
  an item starts at the section's base indentation, and a new item starts only
  after the previous one has shown its arrow or after a deeper-indented
  continuation (the end of the previous item's text). That keeps a left side
  that wraps over two lines (e.g. "the tail shows a concentrated" / "cause
  -> ...") in one item while still separating arrow-less items like the NOT
  DISPATCHING rows, which the real file does.
- `parse_workbench()` (`scripts/dashboard.py:941`) yields the preamble (text
  before the first heading) plus one section per heading that actually
  appears. A missing heading simply has no section.
- `render_workbench_sections()` (`scripts/dashboard.py:974`) lays QUEUED and
  CONDITIONS split items out in a two-column row (thing or condition left,
  arrow, release or consequence right) and shows every other item verbatim in
  a `<pre>` with its original line breaks.

The fallback is demonstrated by `test_workbench_drift_fallback()` on a
deliberately malformed input (heading "NOT DISPATCHING, AND WHY" missing, an
item with no arrow, an item ending in a dangling `<-`). It parses without
crashing, the missing heading yields no block, the unsplit item stays whole,
the dangling arrow is kept verbatim, and a per-line loop proves every
non-blank line of the input still appears in the rendered HTML. Nothing the
orchestrator wrote can be dropped: the only lines that do not appear verbatim
in the rendered output are the arrow-bearing lines, whose arrow becomes the
split point and whose two sides are both rendered.

The current `_build/workbench.md` (which a parallel dispatch updated mid-task
to add a "dark mode for the board" queued row) parses as: preamble, then all
four headings, QUEUED as 3 split rows, CONDITIONS as 3 split rows (including
the two wrapped left sides), and NOT DISPATCHING as 3 verbatim blocks with
all 7 lines intact.
