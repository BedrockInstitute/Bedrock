## GOAL

**Two agents returned and nobody knew for 52 minutes.** Their slots sat idle
the whole time. The owner called this unacceptable and is right: idle slots are
the one defect this orchestration is supposed to make impossible (PLAN D23),
and a notification path that fails silently defeats every other guard.

The orchestrator has patched the two proximate causes. **Your job is to assume
the patch is insufficient and prove it.** Find the remaining ways a return can
go unannounced, and rank them by how long the resulting idle window would be.

**Bias your search toward silent failure.** A crash that prints something is a
nuisance; a return that produces no signal at all is the actual bug class here,
because nothing downstream ever notices. Prefer one reproduced silent-failure
path over five cosmetic findings.

## WHAT HAPPENED, PRECISELY

The tool is `.claude/skills/codex-dispatch/dispatch.py`. Agents are launched
with `start_new_session=True` (setsid) so that killing whatever launched them
cannot take them down; two agents were lost that way earlier the same day. The
price of that detachment is that the orchestrator's harness cannot see them, so
a separate `wait` process is armed as a harness-tracked background job, and its
EXIT is the notification. One waiter, one notification.

The two proximate causes, both now patched:

1. **`wait --all` waits for the slowest.** `T70` finished early and its signal
   was held behind a still-running sibling. The default (first-return) is now
   documented as the right choice and `--all` carries a warning.
2. **The watch set was snapshotted at start.** `T72` was dispatched after the
   waiter was armed and was therefore never watched at all. `wait` now re-scans
   each tick and adopts new agents.

Three alarms were added: `wait` marks each announced return with a `reported`
flag and prints loudly which agents are still running and now unwatched;
`status` screams about any exited agent whose return was never reported; and
every `run`/`queue` prints a reminder to arm the notifier.

## WHAT TO ATTACK

Cover all of these, and say for each whether the path is now safe, with the
command and output that shows it:

**The waiter's own life.** What if the waiter dies (killed, crash, machine
sleep)? What if it is never armed at all? What if two waiters run at once, do
they both report, and does the `reported` flag race? What if the waiter is
armed when nothing is running? What if an agent exits in the same tick the
waiter adopts it?

**The `reported` flag.** It is written under the registry lock; is it written
on every path that announces a return, and only then? Can a return be marked
reported without anyone having been told, for instance by a waiter that exits
for another reason? Can the flag be lost by a concurrent registry write? What
happens to it on `resume`, which creates a new task key?

**The `status` alarm.** It filters on `started` beginning with "2026", which is
a crude guard; what breaks in 2027, and what breaks for a record written by an
older version without that field? Can the alarm be silenced accidentally? Does
it fire for an agent that is still running but whose process died in a way
`alive()` misreads?

**The detachment boundary.** Agents are setsid'd, so nothing but the registry
knows they exist. If the registry is lost or corrupted (there is a recovery
path that moves it aside), are the live agents then invisible forever? Is there
any way to re-discover a running agent that is not in the registry, and does
`status`'s stray detection actually cover that case?

**The gap between exit and audit.** The notification says an agent returned;
what if it returned having written nothing (killed, budget-exhausted)? Does the
path distinguish that clearly enough to act on, and does the reminder to
`resume` reach the right place?

**Timing.** The waiter polls every 15 s. Is the worst-case latency bounded by
that, or by something else? Is there any path where a return is noticed only on
the NEXT dispatch, which could be hours?
