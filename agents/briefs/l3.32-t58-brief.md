## GOAL

`.claude/skills/codex-dispatch/dispatch.py` is a new wrapper that every Codex
sub-agent for this project is now launched through. It exists to make three
classes of dispatch failure impossible rather than merely documented. **Try to
break it.** Find the scenarios and edge cases where it does the wrong thing,
and prove each finding by running it, not by reading it.

**This tool guards the orchestration of every other agent, so a defect here is
multiplied across every dispatch that follows.** A silent wrong answer from it
is worse than a crash: the failures it was built to prevent were all silent.

## WHY IT EXISTS (the three failures it was built against)

All measured 2026-08-05, all silent, all producing a log that stops mid-sentence
and reads exactly like a crash:

1. **A dead model.** Dispatching with `-m deepseek-v4-pro`, which this backend
   rejects until early August 2026. The agent exits in seconds having written
   nothing.
2. **A self-blocking sandbox.** Dispatching a brief that orders "write your
   report to `_build/x.md`" under `-s read-only`, which blocks the agent from
   writing its own report. One 34-row sweep survived only because its final
   message happened to carry the text.
3. **A process-group kill.** A backgrounded watcher shell that waited for a
   free slot and then launched an agent owned that agent; stopping the watcher
   killed the agent. `nohup` does not prevent this. Two agents lost. The same
   watcher also counted ITSELF when it polled `pgrep -f 'codex exec'`, because
   its own command line contains the brief text, so it left a slot idle.

## THE SCENARIOS TO COVER

Cover every one, and say for each whether it behaves correctly, with the
command you ran and its output:

**Normal paths.** A fresh Agda dispatch; a fresh non-Agda dispatch; a queued
dispatch that waits and then fires; a resume of a killed agent; `status` with
nothing running; `status` with a mix of live, exited-clean and exited-without-a-
final-message; `check` on a good brief and on each kind of bad brief.

**Concurrency and state.** Two invocations racing for the last free slot (is
the slot count read-then-write without a lock?). Two queued waiters both seeing
the same free slot. A queued waiter whose task name collides with a running
one. Whether a non-Agda agent can be made to consume an Agda slot, or an Agda
agent to escape the ceiling by omitting the flag.

**The registry as a data structure.** A corrupt or truncated `registry.json`. A
registry entry whose PID has been recycled by an unrelated process, which would
report a dead agent as RUNNING and hold a slot forever. Unbounded growth. A
registry written by two processes at once. Missing keys in an old record.

**Resume.** Resuming an agent whose session id was never captured (the scraper
polls for a bounded time: what if the id is printed later, or never?).
Resuming a task whose brief has since been edited or deleted. Resuming twice.
Resuming something still alive. Whether the log of a re-run or resumed task
overwrites the forensic record of the previous attempt.

**Validation.** Find briefs the `orders_write` detection MISSES, which would let
a report-writing brief through under read-only. Find briefs it flags wrongly.
Is `--sandbox read-only` compatible with `--agda` at all, given that Agda writes
interface files? Does the model block have a way to be lifted when the model
becomes available, or will it wrongly refuse forever?

**Stray detection.** Whether it can produce false positives (a codex process
from an unrelated project or an earlier session) or false negatives (a
hand-launched agent it fails to notice). What it does when `ps` output is
unexpected.

**Ergonomics that become correctness.** Does a refusal always say what to do
instead? Can a refusal be misread as a launch? Does anything print success
before the agent is actually running?
